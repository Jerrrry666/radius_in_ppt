### 1.3 修 bug #2 + 新发现的子 bug：4 个子只写 2 个 ✅

**用户实测现象**：
- 2×2 布局
- 在 PPT 里直接拖父的 R 角黄色滑块（不走 task pane onApply）
- 之前：完全没联动（v1.2.1 报过）
- 修完 v1.3.6 第一次跑：上面 2 个子变了，下面 2 个没变

**新发现的根因（v1.3.6 修）**：
- `radius-core.syncLayoutChildrenR` / `applyLayout` 内部调 `writeRadius`，而 `writeRadius` 内部 `readTag` 调 `ctx.sync()`。
- 4 个子 = 4 次 `readTag + ctx.sync()` + 4 次 `setAdjFraction`。
- **Mac LTSC 真实 PPT 上 per-call sync 在 for 循环内累积**（v1.2.6 注释过这个坑），后几个 shape 的 `setAdjFraction` 失败/丢失。
- 表现为：4 个子只写 2 个（z-order 关系可能也有关：上面 2 个写成功，下面 2 个写丢失）。
- mock harness 不模拟这个 PowerPoint 内部状态，所以单元测试一直过、实测一直炸。

**修法**（核心）：
- 走 `driver.readTagsBulk` 一次拿全部 tag（不调 per-shape ctx.sync）—— 这个函数 v1.2 期间已经加到 driver / test-harness，**但 radius-core 一直没用**。
- `writeRadius` 加 `opts.knownLockState` 入口，caller 已知 lock + strict 就不调 readTag。
- `syncLayoutChildrenR` / `applyLayout` 改成：一次 load + sync 拿全部 + readTagsBulk + 写所有 setAdjFraction + final sync。

**单测覆盖**：
- `bug #6 子 bug：syncLayoutChildrenR 写 4 个子（2×2）→ 全部写进去`（验证 4 个子 adjFraction = 0.5）
- `bug #6 子 bug：applyLayout 写 4 个子（2×2）→ 全部写进去`（同样验证）
- `bug #6 子 bug：writeRadius opts.knownLockState 跳过 per-call readTag`（验证 call 计数 = 0 readTag）

### 1.4 修 bug #3：lockMonitor 偶发 GeneralException ✅

**根因**：跟 bug #2 同一类坑。`monitorTick` 1365-1459 行的 for 循环里**每个 shape 都 `await driver.sync()`**（per-shape get(0) + per-shape sync 模式，v1.0 写法）。多个 shape = 多次 ctx.sync()，Mac LTSC 偶发 `GeneralException`。

## v1.2.8 (2026-07-25) — ⚠️ 圆角风格切换：标准 G1 / iOS 风格 G2 数学参考（已被 v1.2.10 回滚）

> **回滚说明**：用户实测后认为 v1.2.8 的"圆角风格" UI（"🍎 iOS 风格" radio + 强度滑块 + squircle 几何参数 readout）"没有用"。v1.2.10 把这一段 UI、相关的 `computeSquircleHint` / `IOS7_DEFAULT_SMOOTHING` 函数、9 个单测、相关 CSS 全部回滚。v1.2.8 tag 在 origin 保留作为历史（实现可参考），v1.2.10 是不含这段代码的 active 版本。**功能上 v1.2.10 ≡ v1.2.7 + size 联动**。

### 背景（保留作为研究记录）
用户在 v1.2.7 后提了"苹果风格的连续曲率圆角"（squircle / G2 continuity）。研究后发现：
- iOS 7+ 圆角不是普通圆角，是 1 段 1/4 圆弧 + 2 段贝塞尔曲线的复合（G2 连续曲率）
- Figma 2017 年 *Desperately Seeking Squircles* 把它工程化，公式是 cornerSmoothing 0-1
- iOS 7 app 图标用 smoothing ≈ 0.6（Apple 默认）
- **PowerPoint 圆角矩形只支持单段 90° 圆弧（adjustment value 0-1）**，无法写入多段贝塞尔

### 方案
在 dialog 加"圆角风格"radio：
- **标准圆角 (G1)** — 默认，跟 v1.2.7 行为完全一致（写入 PPT 的就是普通圆角）
- **🍎 iOS 风格 (G2 continuous)** — 选中后：
  - 展开平滑强度滑块（默认 60%，iOS 7 默认值）
  - 显示 Figma squircle 公式算出的理论几何参数（p / arc 度数 / a / b / c / d）
  - 警告「PPT 原生圆角矩形不支持 G2 贝塞尔，强度仅作视觉参考」
  - toast 提示用户当前 R 角会按标准圆角写入

### 实现

**1. `radius-core.js`：加 `computeSquircleHint(rCm, smoothing)` 纯函数 + `IOS7_DEFAULT_SMOOTHING = 0.6`**

公式（参考 Figma 文档 figure 12.2 + MartinRGB 反编译的 rounded-corners.js）：
```
p = (1 + smoothing) * R
arcMeasure = 90° * (1 - smoothing)
arcLength = sin(arcMeasure/2) * R * √2
alpha = (90° - arcMeasure) / 2
p3ToP4 = R * tan(alpha/2)
beta = 45° * smoothing
c = p3ToP4 * cos(beta)
d = c * tan(beta)
b = (p - arcLength - c - d) / 3
a = 2b
```

返回 `{ pCm, arcMeasureDeg, arcLengthCm, betaDeg, cCm, dCm, aCm, bCm, figmaEquivalent }`，UI 用这些值展示。

**2. `dialog.html`：加"圆角风格"section**

放在"应用 R 角"按钮下面，结构：
- 2 个 radio（standard / ios）
- ios 模式展开 panel：强度滑块 0-100 + readout 文本框（等宽字体显示几何参数）+ 警告文字

footer 更新到 "v1.2.8 · 圆角风格切换（标准 G1 / iOS 风格 G2 数学参考）"。

**3. `dialog.css`：加 corner-style-group / ios-style-panel / ios-squircle-readout / ios-style-warn 样式**

橙色配色（`#ff9500` / `#ff6b00` / `#b85c00`）跟 iOS 风格视觉一致，readout 用 `ui-monospace` 等宽字体显示。

**4. `dialog.js`：加 iosStyleEnabled / iosStyleSmoothing state + renderIosStyleReadout + 事件绑定**

- `renderIosStyleReadout()` 在 renderUI 末尾调用，按当前 R 角 + smoothing 算几何参数
- radio 切换 → 显示/隐藏 panel + toast 提示
- 滑块 input → 更新状态 + 实时重算 readout
- onApply 末尾 toast 加 `· 🍎 iOS 风格参考 ×%` 后缀

### 测试

新增 9 个 computeSquircleHint 纯函数测：
- smoothing=0 → 完全退化（arc=90°, a=b=c=d=0）
- smoothing=0.6 (iOS 7) → arc=36°, beta=27°, figmaEquivalent='iOS 7+ 风格 (G2)'
- smoothing=1 → arc=0°（圆弧被贝塞尔吞掉）
- smoothing 越界 → clamp 到 [0, 1]
- R 角缩放：所有几何参数线性缩放（cm 维度 2.5x，度数不变）
- R=0 → 全 0
- 非有限输入 → 当 0 处理
- IOS7_DEFAULT_SMOOTHING = 0.6
- figmaEquivalent 标签分档（0/0.3/0.6/0.7/0.9）

**总测试数**：175 全过（86 features + 89 radius-core，含 9 个新测）

### 限制（已知 / 不修）

- **PowerPoint 圆角矩形只支持单段圆弧**：无法写入 G2 贝塞尔曲线
- **真正 G2 squircle 需要嵌入 SVG 路径**（v1.2.8 不做，会破坏形状语义）
- **UI 加"iOS 风格"模式只是视觉参考 + 标签**：实际写入 PPT 的仍是普通圆角

## v1.2.9 (2026-07-25) — Layout 父 size 变化时子图形 size 跟随

### 背景
v1.2.4-v1.2.8 已经实现了：父 R 角变化时子 R 角跟随 + autoPadding 自动重算子位置/尺寸。但**父的 width/height 变化时子不会跟随**——用户反馈"调整父 R 角时子会变，但调整父 size 时子不变"。

### 根因
- `monitorTick` 只通过 `detectLayoutParentChanges` 检测 R 角变化
- 父的 width/height 变化完全没被检测
- `applyLayoutToChildren` 内部已经会按当前父的 size 重算 subW/subH + 子位置/尺寸 + R 角，但需要 caller 触发
- 缺一个"父 size 变化检测器"

### 实现

**1. `radius-core.js`：加 `detectLayoutParentSizeChanges(knownSizeMap, selectedShapes)` 纯函数**

跟 `detectLayoutParentChanges` 并列，caller 跑两个检测 → 任一变化都 fire `scheduleParentRSync`。

```js
function detectLayoutParentSizeChanges(knownSizeMap, selectedShapes) {
  // 对每个 layoutRole === 'parent' 的形状：
  //   - 读 widthCm / heightCm（兼容 width / height pt 字段）
  //   - 比 knownSizeMap[parentId] 容差 1e-3 cm（≈ 0.028 pt）
  //   - 变了 → push { parentId, lastSize, newSize }
  //   - 首次见到（lastSize null）→ push { lastSize: null }（caller 决定 fire）
  //   - 非 parent / 缺 size 字段 / lastSize NaN → 跳过
}
```

**2. `dialog.js`：monitorTick 末尾加 size 联动检测**

```js
// 跟 R 角检测合并：任一变化都触发 scheduleParentRSync
const rChanges = detectLayoutParentChanges(lockMonitor.lastCm, selectedShapes);
const sChanges = detectLayoutParentSizeChanges(lockMonitor.lastSizeCm, selectedShapes);
// ...更新 lastCm / lastSizeCm，有变化就 fire
```

state 加 `lockMonitor.lastSizeCm = {}`（startLockMonitor / stopLockMonitor 都清空）。

诊断 log 加 `[layout-link] SIZE-fire parentId=...` 区分 R-fire。

### 触发路径（关键）
用户在 PPT 里：
- 拖父的 R 角黄色滑块 → `lastCm` 变 → R-fire → applyLayoutToChildren → 重算 layout 几何 + R 角
- **拖父的边缘/角控制柄改 size** → `lastSizeCm` 变 → **SIZE-fire** → 同样调 applyLayoutToChildren → **重算 layout 几何 + R 角**

applyLayoutToChildren 是统一入口，size / R 任一变化都走它，所以子位置/尺寸/R 角都会自动跟上。

### 测试
新增 10 个 `detectLayoutParentSizeChanges` 纯函数测：
- 父 width 变了 → 返回 changed
- 父 height 变了 → 返回 changed
- 容差内 → 返回空
- 首次见到 → lastSize null
- 非 layout 父 → 跳过
- 兼容 width/height 字段（pt 自动转 cm）
- 缺 size 字段 → 跳过
- lastSize 字段损坏（NaN）→ 当首次
- selectedShapes 非数组 → 返回空
- 多个父混合（部分变 + 部分首次）→ 只返回变了的

**总测试数**：185 全过（89 features + 96 radius-core，含 10 个新测）

### 限制（已知 / 不修）
- 拖动过程中节流 200ms 才 fire（避免每 10ms tick 都开 PowerPoint.run），视觉上看子会"跟一下"父
- 启动时首次见到只记 lastSize，不 fire（避免启动时无意义重写子 R 角 / size）
- 跟 v1.2.4 bug #2 教训一致：monitorTick 走 per-shape get(0) + per-shape sync 模式（v1.0 风格），不靠 collection-level load + new get(0)（Mac LTSC proxy snapshot 失效）

## v1.2.11 (2026-07-25) — 行/列互斥联动（行 × 列 = 子数 N）+ 单滑块 UI

### Bug
用户实测报 bug：2×2 布局（共 4 个子），把「行」从 2 改成 1，结果变成了 **1×2**，而不是期望的 **1×4**。

### 根因
v1.2 之前行/列是 2 个独立滑块（min=1, max=5, step=1），各自的范围互不相关。改 rows=1 → cols 保持原值 2 → 1×2，剩 2 个子没动。

而且这违反了 layout 的核心约束：**layout 一旦创建，rows × cols 必然等于子数 N**（4 个子排成 2×2 是 4 个位置 = 4 个子）。rows 和 cols 不应该独立。

### 修法

**1. `radius-core.js`：加 `computeGridCoupledRowsCols(changed, value, N)` 纯函数**

```js
function computeGridCoupledRowsCols(changed, value, N) {
  // clamp value 到 [1, N]
  // 改 rows → cols = max(1, ceil(N / rows))
  // 改 cols → rows = max(1, ceil(N / cols))
  return { rows, cols }
}
```

例子（N=4）：
- `computeGridCoupledRowsCols('rows', 1, 4)` → `{ rows: 1, cols: 4 }`（1×4，4 个子全用上）
- `computeGridCoupledRowsCols('rows', 3, 4)` → `{ rows: 3, cols: 2 }`（3×2，4/3 上取整 = 2）
- `computeGridCoupledRowsCols('rows', 10, 4)` → `{ rows: 4, cols: 1 }`（clamp 到 N=4）

**保证：`rows × cols >= N`**，所以 N 个子全用上、不被丢。

**2. `dialog.js`：行/列 UI 改单滑块 + 列 readout**

- 删 layout-cols 滑块和数字输入（用户不需要再改列）
- 改用 layout-cols-readout 文本（蓝色 badge 显示当前列值）
- 上侧滑块拖行（橙色「行」tag + 数字输入 + 滑块）
- 下侧只读列值（蓝色「列」tag + readout + "（自动 = N ÷ 行）"提示）
- slider max 跟 N 走（renderLayoutPanel 里 `rowsR.max = String(N)`），不是硬编码 5
- N=1 时 slider 禁用（1×1 唯一），显示"（只有 1 个子）"
- tag 损坏 / 旧版 layout（rows × cols != N）→ 自动归一化到 rows=N, cols=1

**3. `bindLayoutGridRangeAndNum` 改新签名**

```js
bindLayoutGridRangeAndNum('layout-rows', 'layout-rows-num', 'layout-cols-readout')
```

只有 3 个 id（rows slider + rows num + cols readout），列不再有独立 input 元素。

### UI 视觉效果
之前：
```
行 [——●——] 2
列 [——●——] 2
```

现在（v1.2.11）：
```
行/列  [行]  [——●——] [2]    ← 上行：橙色 tag + 滑块 + 数字
        [列]   2  (自动 = 4 ÷ 行)  ← 下行：蓝色 tag + 蓝色 badge + 提示
```

拖滑块时只有行变，列 badge 实时同步（ceil(N/rows)）。视觉上一眼看出"行 = 我拖的，列 = 自动算的"。

### 测试
新增 14 个 `computeGridCoupledRowsCols` 纯函数测：
- N=4 各 case（rows=1/2/3/10 + cols=3）
- N=1 边界（任何值都 1×1）
- N=6 各种 case
- 改 rows=0 / -3 → clamp 到 1
- 非有限输入（NaN/undefined/3.7）→ 当 1 处理
- N=0 防御 → 1×1
- changedKey 非法 → 按 cols 处理
- **核心不变量** `rows × cols >= N`：11 个 N 值 × 5 个 v 值 × 2 个 changedKey = 110 个断言全过

**总测试数**：190 全过（89 features + 101 radius-core，含 14 个新测）

### 父图形 size 不动
applyLayoutToChildren 内部逻辑：读父 box（line 650 `driver.box(parentSh)`）→ computeLayout 算子位置/尺寸 → 写子 setBox。父的 left/top/width/height 从未被写过。用户的明确要求"父图形的尺寸等都不要变动"自然满足。

## v1.2.12 (2026-07-25) — 修 v1.2.11 行/列联动 bug：字符串 value 被 fallback 到 1

### Bug
v1.2.11 后用户实测：2×2 布局改行到 1 → 1×4 ✓，但**改不回去了**——拖到 2、输入 2、输入 3 都没反应，rows 永远停在 1。

### 根因
`computeGridCoupledRowsCols(changed, value, N)` 写的时候假设 `value` 是 number，但 slider 和 number input 的 `value` 都是 **string**（"1" / "2" / "3"）。

```js
let v = Number.isFinite(value) ? Math.floor(value) : 1;
//                                ↑ "2" 是 string → Number.isFinite("2") === false
//                                → v fallback 到 1（任何字符串都返回 1）
```

所以**任何**字符串 value 都返回 1×N 布局。拖到 1 是「刚好对」，拖到 2 变 1×N 又回不去——因为又回到 1。

### 修法
```js
const numValue = Number(value);
let v = Number.isFinite(numValue) ? Math.floor(numValue) : 1;
```

`Number("2")` = 2（数字），`Number.isFinite(2)` = true，正常走 v=Math.floor(2)=2。`Number("abc")` = NaN，`Number.isFinite(NaN)` = false，fallback 到 1。

**测试用例补全**：新增"字符串输入（slider / number input 真实场景）"测，覆盖 `"1"` / `"2"` / `"3"` / `"4"` / `"2.7"` / `""` / `"abc"` 7 个 case。

**总测试数**：191 全过（89 features + 102 radius-core，含 1 个新测覆盖 7 个字符串 case）

### 教训
写纯函数时默认 `value` 是 number 是高风险假设。slider / number input / dataset 属性等 DOM 来源全是 string。要么在 caller 转，要么在函数内 `Number(value)` 兼容。
